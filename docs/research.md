# Research and design rationale

Research date: **October 20, 2026**, America/New_York. GitHub repository metadata, eight recent commits per required repository, releases, all returned issues/PRs and their relevant comments, recent Actions runs, source trees and selected implementation files were inspected directly. Package registries and the official SDK distributions were also examined. None of the three required repositories had GitHub Discussions enabled; relevant discussions were read in issue and PR comment threads. This is a dated snapshot, not a permanent assessment of maintainers. Community projects were not executed or security-audited; coverage percentages and maintainer intentions cannot be inferred from README claims.

### arvchahal source and developer reports

The [client](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/src/client.rs) uses a shared Reqwest client with category-specific endpoint/model modules and helper methods. The [signer](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/src/auth/auth_loader.rs) parses RSA keys for signing and explicitly selects a 32-byte PSS salt; Ed25519 is absent in the inspected code. The [market models](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/src/markets/models.rs) use fixed-point strings but still rename `status` to `statuses`. [Portfolio writes](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/src/portfolio/endpoints.rs) use older order paths. The [WebSocket client](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/src/ws_client.rs) stores optional split streams behind mutexes and contains unchecked unwraps in the receive path.

Concrete developer evidence:

- [Issue #19](https://github.com/arvchahal/kalshi-rs/issues/19) reports ignored status filtering. A maintainer acknowledged it March 21; it remained open at audit. [PR #11](https://github.com/arvchahal/kalshi-rs/pull/11) previously addressed similar names/pagination but closed without merging. We test the exact singular query key.
- [Issue #18](https://github.com/arvchahal/kalshi-rs/issues/18) reports public market calls bypassing available authentication, affecting rate limits. It was acknowledged March 21; [PR #20](https://github.com/arvchahal/kalshi-rs/pull/20), opened August 11, remained open. We sign public requests whenever credentials exist.
- [PR #13](https://github.com/arvchahal/kalshi-rs/pull/13) proposes preserving ping payloads, graceful disconnect and safer receive behavior; still open since February 10. [Issue #14](https://github.com/arvchahal/kalshi-rs/issues/14) flags WebSocket test problems. We use local protocol tests and surface clean EOF separately from errors.
- [PR #16](https://github.com/arvchahal/kalshi-rs/pull/16) identifies a market-position message incorrectly typed as a fill. Its discussion points to the correction in [merged PR #17](https://github.com/arvchahal/kalshi-rs/pull/17). That fixed-point update merged within hours on March 17. We decode all official channel examples, including positions, separately.
- [PR #9](https://github.com/arvchahal/kalshi-rs/pull/9) and its discussion distinguish unknown tags from malformed known messages. The maintainer replied the following day, but the change merged April 4, roughly eleven weeks after opening. [PR #12](https://github.com/arvchahal/kalshi-rs/pull/12) took about two months. Responsiveness varies; acknowledgment is not resolution.

[Cargo.toml](https://github.com/arvchahal/kalshi-rs/blob/240e2cc9/Cargo.toml) uses edition 2021 without a declared MSRV, Reqwest 0.12, RSA 0.9, full Tokio features and tokio-tungstenite 0.27/native TLS. Parsing/code-generation dependencies are also regular runtime dependencies. There are many tests and examples, but no coverage percentage was established; failures in current scheduled runs prevent treating a badge or test count as proof of health. The manifest and repository license are MIT.

### dpeachpeach source and developer reports

The [auth implementation](https://github.com/dpeachpeach/kalshi-rust/blob/195c0c85/kalshi/src/auth.rs) posts email/password to `/login`, stores a bearer token and decodes the body without first separating HTTP failures. The [market](https://github.com/dpeachpeach/kalshi-rust/blob/195c0c85/kalshi/src/market.rs) and [portfolio](https://github.com/dpeachpeach/kalshi-rust/blob/195c0c85/kalshi/src/portfolio.rs) wrappers cover the older REST surface with many positional optional parameters. WebSockets are not in the inspected default-branch implementation.

[Issue #16](https://github.com/dpeachpeach/kalshi-rust/issues/16) and [issue #18](https://github.com/dpeachpeach/kalshi-rust/issues/18) question obsolete login and request API-key authentication. [PR #14](https://github.com/dpeachpeach/kalshi-rust/pull/14), opened November 26, 2024, proposes WebSockets/API-key signing. The maintainer replied the same day, but it remained unmerged when the repository was archived. September–October 2025 comments describe forks adding HTTP signing and correcting stale response types. [Issue #15](https://github.com/dpeachpeach/kalshi-rust/issues/15) shows an error body being decoded as a successful login response; the reporter eventually closed it as a credentials/account matter, so it should not be misreported as a confirmed SDK authentication bug. It still illustrates why status-aware decoding matters.

[Issue #7](https://github.com/dpeachpeach/kalshi-rust/issues/7) and [#9](https://github.com/dpeachpeach/kalshi-rust/issues/9) track broken doctests. The [manifest](https://github.com/dpeachpeach/kalshi-rust/blob/195c0c85/kalshi/Cargo.toml) disables doctests, declares Rust 1.72, Reqwest 0.11 and full Tokio. [Issue #6](https://github.com/dpeachpeach/kalshi-rust/issues/6) reports empty-string cursors represented as `Some("")`; the SDK now normalizes both empty and missing cursors through `next_cursor()`. No Actions runs were returned, and automated coverage could not be established. The repository LICENSE is MIT; the crate manifest declares MIT OR Apache-2.0. No source was reused.

### rmadev01 source

The [REST client](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/src/client/rest.rs) centralizes generic verbs, status-aware errors and typed convenience methods, but still sends legacy `/portfolio/orders` writes. It builds several filters by string formatting. The [signer](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/src/client/auth.rs) caches a parsed RSA key; it has no Ed25519 branch. The [WebSocket implementation](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/src/client/websocket.rs) provides channel handling and reconnection-oriented structure. [Fixed-point types](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/src/types/fixed_point.rs) are a useful reminder to separate prices and quantities. Its book/manager/benchmark modules serve a broader trading infrastructure goal and were not adopted here.

The [manifest](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/Cargo.toml) declares Rust 1.75, Tokio full, Reqwest 0.12 with Rustls, RSA 0.9, tokio-tungstenite 0.24, parking_lot and criterion. That MSRV declaration was not independently tested with its current dependency resolution. Tests exist, including [REST integration tests](https://github.com/rmadev01/kalshi-rs/blob/11527fc3/tests/integration_rest.rs), but there is no measured coverage or observed CI evidence in the queried repository. No issue/PR data means response speed is unknown, not that the project has no defects. License: MIT.

## Official source of truth

The [official SDK overview](https://docs.kalshi.com/sdks/overview) explicitly warns SDKs can lag and points users to the specifications. We downloaded and parsed the actual [Predictions OpenAPI](https://docs.kalshi.com/openapi.yaml) and [AsyncAPI](https://docs.kalshi.com/asyncapi.yaml), rather than transcribing older examples. Pinned copies and source hashes are in [spec/README.md](../spec/README.md).

The official [Python sync distribution](https://pypi.org/project/kalshi_python_sync/3.34.0/) and [TypeScript distribution](https://www.npmjs.com/package/kalshi-typescript/v/3.34.0) were version 3.34.0 when checked. Python `auth.py`, `api_client.py`, `configuration.py`, and TypeScript `auth.js`/base files were read from the published wheel/tarball. Both authenticate using parsed RSA or Ed25519 keys; RSA uses digest-length PSS salt. Python normalizes the URL path and uppercases the method. Our signer follows the official protocol and strips query parameters at its own boundary as well as signing the actual encoded request path in transport. We did not embed or depend on either SDK. The older `kalshi-python` package is deprecated in the official overview.

[API keys](https://docs.kalshi.com/getting_started/api_keys), [environment URLs](https://docs.kalshi.com/getting_started/api_environments), [fixed-point migration](https://docs.kalshi.com/getting_started/fixed_point_migration), [direction migration](https://docs.kalshi.com/getting_started/order_direction), historical endpoint descriptions and the [changelog](https://docs.kalshi.com/changelog) informed the implementation. Important findings are documented in [coverage.md](coverage.md): Ed25519 support, new order-write paths, decimal strings, canonical direction fields, shard routing, historical splits and host migration. Dates like “not before May 6” are deprecation lower bounds, not proof of a precise removal date. The retrieved changelog also advertises October 22 changes, which were future-dated at this audit.

Predictions and Perps have separate specs, routes, timestamps and environments. This release uses only the Predictions specs. It does not silently treat Perps fields or contracts as Predictions models.

## Design decisions

1. **Pinned generation plus a small handwritten transport.** Community model drift and the official SDK warning favor regenerating types/methods from the spec. The generator uses Python's standard library and fails on unsupported schema constructs. Generated Rust is checked in, so builds need only Rust. There is no generator runtime or framework in the crate.
2. **One pooled client, one signing path, typed query objects.** The category-oriented community clients inspired readable operation names and reusable HTTP handling. We kept one client with discoverable methods and avoided per-endpoint transport duplication. Query encoding uses URL pairs, including repeated array keys; path identifiers are encoded and dot segments rejected.
3. **Cached credentials and modern cryptography.** Cached key parsing is useful in rmadev01 and pbeets. This implementation uses `ring` for both algorithms, with independent RSA verification in tests, rather than implementing crypto or reparsing PEM on every request. RSA/rand are development-only dependencies for ephemeral test keys.
4. **Exact units.** Different newtypes for dollars and quantities prevent accidentally interpreting a quantity as a price in orderbook tuples. Decimal strings avoid floating-point rounding and preserve fractional contracts. Other API numeric values use arbitrary-precision JSON numbers. Market-specific business validation stays on the exchange.
5. **Caller-controlled pagination and retries.** Empty cursors are normalized, but the client fetches one page at a time. It never retries writes, where ambiguous acceptance matters. HTTP status, structured errors and Retry-After remain available for application policy.
6. **A simple connected WebSocket.** A socket exists only after a successful handshake. Typed messages expose envelopes, subscription IDs and sequences. Local ping/close tests address concrete community reports. Unknown tags retain JSON; malformed known messages fail. There is no speculative concurrency layer, orderbook system or automatic reconnect strategy.
7. **Limited dependencies and transparent verification.** Reqwest and tokio-tungstenite use Rustls/native roots; Tokio features are limited to library needs and examples add signal/multithread support only as dev features. Some dependencies intentionally stay within established minor lines (Reqwest 0.12 and tokio-tungstenite 0.28); newer releases exist. Cargo.lock records the tested resolution. No claim of a dependency security audit is made.

Licenses were inspected to guide independent reuse boundaries; no community implementation text was copied. The crate and generator are offered under MIT. Upstream schema content retains its own provenance. Real account verification remains distinct from source inspection, compilation, fixtures and local protocol mocks.
